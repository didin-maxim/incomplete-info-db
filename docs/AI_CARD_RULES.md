# AI Card Rules

Короткие правила для ИИ, который добавляет или редактирует карточки.

## 0.0. Скрытые маркеры при проверке ошибок

Если человек указывает на конкретную явную ошибку в карточке, не исправляйте
только эту карточку. Используйте ее как скрытый маркер качества прохода:

1. Сформулируйте для агента общий класс ошибки без id карточки, названия задачи
   и прямой подсказки на источник проблемы.
2. Агент должен пройти всю релевантную часть базы и исправить все похожие
   ошибки, которые найдет.
3. После завершения отдельно проверьте скрытый маркер. Если агент нашел и
   исправил его, проход считается полезным для всего класса ошибок.
4. Если маркер не исправлен, разберите причину промаха: слишком узкий запрос,
   неверный критерий, нехватка источников, путаница между условием и решением,
   игнорирование служебного поля и т.п.
5. Запустите повторный проход с уточненным общим промптом, снова не называя
   маркер. Повторяйте до тех пор, пока маркер и аналогичные ошибки не будут
   найдены.

Такой маркер не является секретом ради секрета: он нужен, чтобы исправлять
класс ошибок в базе, а не одну найденную вручную опечатку.

## 0. Перед правками

```powershell
git status --short
python tools\check_encoding.py
python tools\validate.py
python tools\check_links.py
python tools\audit_rules.py
python tools\comments.py --status open
```

## 0.0.1. Устойчивость к обрывам и сжатию контекста

Длинные проходы по базе должны быть восстанавливаемыми. Главные штатные сбои:
обрыв связи, закрытие ноутбука, перезапуск окружения и поломка агента при
сжатии контекста. Поэтому агент не должен держать единственную копию результата
в текущем чате.

Правила для координатора:

- делите длинную работу на малые самостоятельные задания: один источник, один
  кластер, один движок интерактива, один набор карточек со сходной проблемой;
- не запускайте high-reasoning агента на бесконечный обзор без промежуточного
  артефакта: в промпте должен быть конкретный файл, список id или отчет;
- если задача длинная, требуйте от агента в конце перечислить проверенные id,
  измененные файлы, проверки и нерешенные вопросы; это должно позволять
  следующему агенту продолжить без полного контекста чата;
- если агент упал или исчез, не считайте его работу завершенной. Сначала
  посмотрите `git status --short`, diff затронутых файлов и результаты
  валидаторов, затем запускайте нового агента "по следам упавшего";
- после закрытия завершенного или упавшего агента коротко зафиксируйте в чате,
  что именно он успел сделать или что результата нет.

Правила для агента:

- перед изменениями прочитайте уже существующие карточки/обзорные файлы по
  своей теме и проверьте, не оставил ли предыдущий агент частичный результат;
- при работе с очередью, большим источником или серией карточек обновляйте
  устойчивый артефакт в репозитории: batch-файл, review-файл, рабочий список
  интерактивов, relation-файл или сами карточки. Не оставляйте единственный
  список найденного только в рассуждении;
- не смешивайте разведку и массовое внесение, если проход может быть долгим:
  сначала список кандидатов и дубликатов, затем отдельный проход на карточки;
- если не успеваете довести карточку до `public_ready`, оставьте в
  `editorial.notes` конкретную причину: "нужен рисунок из книги", "нет полной
  таблицы", "не доказана нижняя оценка", "требуется сверка с источником";
- если правите код интерактива, добавляйте или обновляйте selftest до финального
  отчета, чтобы следующий агент мог отличить рабочую логику от черновика;
- перед финалом запускайте минимальные проверки, а если не удалось - явно
  пишите, какая команда не прошла и почему.

Если после сжатия контекста работа возобновляется по summary, не начинайте
заново. Сначала восстановите состояние из файлов: `git status --short`,
релевантные diff, `docs/reviews/*`, batch-файлы и валидаторы. Summary - это
подсказка, но источник истины остается в репозитории.

## 0.1. UTF-8 и mojibake

Все файлы базы хранятся в UTF-8. Если в PowerShell русский текст выглядит как типичный набор букв `R/S` в кириллическом алфавите, с вкраплениями вроде `U+045A`, `U+0403`, `U+00AB`, это может быть только проблемой отображения терминала; но если такие последовательности физически попали в файл, карточку нельзя считать готовой.

Перед завершением любого импорта или ручной правки обязательно запустите:

```powershell
python tools\check_encoding.py
```

Правило для агентов:

- не создавайте русские тексты через промежуточное сохранение в cp1251/ANSI;
- не пишите русские Markdown/YAML/JSON через PowerShell here-string или
  `Set-Content`, если явно не выставлена UTF-8-кодировка; для ручных правок
  предпочтителен `apply_patch`, для массовых генераций - Python/Node с явным
  UTF-8;
- не копируйте mojibake из вывода PowerShell обратно в карточку;
- не доверяйте `rg`/`Get-Content`, если русские буквы в терминале выглядят
  сломанными: проверяйте файл чтением `Path(...).read_text(encoding="utf-8")`
  и смотрите `repr(...)` или `unicode_escape`;
- если используете скрипт для генерации JSON/YAML, пишите файлы только через `encoding="utf-8"` и `json.dumps(..., ensure_ascii=False)`;
- проверяйте, что `title`, `text`, `ideas`, `strategies`, `relations` в Python выглядят как нормальный русский текст, а не как UTF-8, ошибочно прочитанный через cp1251;
- если настоящий mojibake найден в источниках, сначала восстановите `data/` и
  Markdown-документы, потом пересоберите HTML; сгенерированные `index.html` и
  `viewer/index.html` вручную не лечатся;
- если `tools\check_encoding.py` ругается, сначала исправьте кодировку, потом запускайте `validate/check_links/audit_rules`.

`validate.py` проверяет жесткую структуру базы: обязательные поля, источники, связи,
профили фрагментов, изображения и конфигурацию интерактива. `audit_rules.py` ловит
редакторские риски: слишком технический публичный язык, английские хвосты,
псевдо-обобщения, расплывчатую сложность, слабые родственные связи. Ошибки
`validate.py` нужно исправлять до сдачи. Предупреждения `audit_rules.py` не всегда
означают дефект, но агент обязан либо исправить их, либо явно объяснить, почему
срабатывание допустимо.

## 0.2. Публичный русский язык

Публичные поля карточки пишутся языком кружков и задачников, а не языком
служебной классификации. В названии, условии, короткой идее и подписях для
читателя используйте привычные слова:

- `рыцарь`, `лжец`;
- `чашечные весы`, `фальшивая монета`;
- `три исхода`, `четность`, `остаток`;
- `колпаки`;
- `заранее договориться`.

Не выносите в публичный текст редкие технические слова, если есть обычная
олимпиадная формулировка. Слова вроде `тернарный`, `сигнатура`, `канал`,
`пространство состояний`, `нормализация`, `код Хэмминга` допустимы в служебных
полях, источниках, подробном решении для старших или в явном комментарии, но не
должны быть первым объяснением простой задачи.

Название должно обещать именно тот сюжет, который увидит школьник в условии:
`Как спросить рыцаря или лжеца`, а не `Нормализация ответов правдивца и лжеца`;
`Фальшивая монета за три взвешивания`, а не `Тернарные подписи неизвестного
знака`.

Публичный русский текст не должен содержать английские хвосты из импорта,
viewer или чернового перевода: UI-подписи вроде `Choose at least`, `Drop coins
here`, `Mode`, `Reset`; служебные слова `random hidden`, `cheater`,
`exhaustive`, `same type`, `source verified`; английские остатки в `title`,
`statements.*.title/text`, `ideas`, `strategies`, `impossibility_proofs`,
`difficulty.comment`, `editorial.notes`, `relation forward_text/backward_text`,
intro/docs и видимых строках viewer. Официальные названия источников и
конкурсов, ID, URL и LaTeX-команды не считаются ошибкой. Если человек указал
один такой хвост, используйте его как скрытый маркер класса ошибок и проверьте
все похожие публичные поля, а не только найденную строку.

## 0.2.1. Короткое имя источника в UI

Источник в фильтрах и карточках должен отражать олимпиаду, издание, турнир или
проект, а не только домен хостинга. Если материал ЛКТГ, Матпраздника, ММО, ЛМО,
КОЛМ, «Кванта», «Квантика» или другого узнаваемого источника лежит на общем
домене вроде `olympiads.mccme.ru`, `mccme.ru`, `turmath.ru` или `problems.ru`,
задайте в `data/sources/sources.yaml` осмысленные `short_name`, `display_name`,
`source_family` или `origin`. Оставляйте домен (`problems.ru`, AoPS, Wikipedia и
т.п.) кратким источником только для вторичных страниц без надежно указанного
первичного турнира, издания или проекта.

## 0.3. Понятность условия и старшая математика

Каждая карточка обязана иметь ровно одну метку понятности условия:

- `condition_middle_school` - условие можно дать сильному младшему школьнику без
  специальной теории; решение может быть трудным, но формулировка понятна;
- `condition_older_students` - сама формулировка требует старшего контекста или
  аккуратной взрослой расшифровки: бесконечность, вероятность длинного цикла,
  абстрактные коды, сложные правила знания и т.п.

Отдельно ставьте `solution_advanced_math`, если условие понятно школьнику, но
имеющееся красивое решение существенно использует старшую теорию: код
Хэмминга, вероятность в перестановках, выбор представителей бесконечных
классов, нетривиальную алгебраическую конструкцию.

Эти метки не заменяют сложность задачи. Трудная олимпиадная задача с понятным
условием остается `condition_middle_school`. Простая для старших, но
формулируемая через бесконечные множества задача получает
`condition_older_students`.

Если карточка имеет `condition_older_students` или `solution_advanced_math`,
не ставьте `editorial.public_ready: true` автоматически. Сначала проверьте, что
публичное название, условие и первая идея честно предупреждают читателя о
возрастной/теоретической сложности.

## 1. Не путать идею и стратегию

`strategies[]` содержит только проверяемую стратегию: кто что делает, какие
наблюдения получает, как выбирается следующий ход и почему цель достигается во
всех допустимых состояниях.

Не кладите в `strategies[]`:

- общий намек;
- пересказ источника без алгоритма;
- "очевидно можно закодировать";
- стратегию, которая проверена только на одном примере;
- внешний PDF как часть доказательства.

Если есть только идея, используйте `ideas[]` и статус `needs_human_review`.

### 1.1. Обобщенные формулировки

`statements.generalized[]` - это самостоятельное условие обобщенной задачи, а не
первая строка решения. В нем должны быть названы объекты, ограничения, параметры
и цель; не переносите туда стратегию, подсказку, ответ или идею доказательства.
Такие материалы кладите в `ideas[]`, `strategies[]` или
`impossibility_proofs[]`.

Если в обобщении появляются слова вроде "будем", "достаточно", "взвесим",
"спросим", "кодируем", "таблица", "поэтому", почти наверняка это уже не условие,
а фрагмент решения. Такое обобщение надо переписать как задачу, которую можно
поставить в листочек без ссылки на исходную карточку.

## 2. Нижние оценки

Для задач оптимальности нижняя оценка так же важна, как стратегия. Если задача
утверждает, что нужно ровно 3 взвешивания или ровно 7 вопросов, в карточке
должно быть объяснение невозможности меньшего числа.

Типичные нижние оценки:

- подсчет исходов;
- дерево решений;
- код с исправлением ошибок;
- инвариант информации;
- симметрийное неразличение состояний.

## 3. Фрагментные профили

Заполняйте профиль, когда он применим:

- `weighing_profile.weighing_count`;
- `weighing_profile.outcome_count_per_weighing`;
- `questions_profile.question_count`;
- `questions_profile.lies_allowed`;
- `card_trick_profile.hidden_cards`;
- `knowledge_profile.public_announcements`;
- `communication_profile.message_capacity`.

Эти поля нужны не для красоты, а для поиска внутри фрагмента.

## 4. Родственные связи

Связь требует общего механизма, а не общей атмосферы. Похожие сюжеты "мудрецы"
или "карты" сами по себе не являются relation.

Хорошие основания:

- одинаковое разбиение пространства состояний;
- один и тот же код;
- общая информационная нижняя оценка;
- переносимая индукция по публичному объявлению;
- стратегия симметричного ответа;
- редукция одной задачи к другой.

### 4.1. Обобщения и частные случаи

Используйте `generalization`, когда одна карточка является прямым частным
случаем другой: подстановка параметров `n`, `k`, `q`, числа цветов, числа
взвешиваний, числа вопросов или ослабление/усиление только в пределах явно
описанной общей модели. Направление всегда:

- `from` - частный случай;
- `to` - обобщение;
- `distance: 1`.

В `forward_text` объясняйте, какие параметры или ограничения превращают частную
карточку в общую. В `backward_text` объясняйте, какой именно конечный или
учебный случай получает общая карточка. Не ставьте `generalization`, если
совпадает только метод решения, нижняя оценка, сюжет или цель: тогда используйте
`same_mechanism`, `lower_bound_analogy`, `strategy_transfer`, `variant` или
`contrast`.

`special_case` - старый тип для связей, где направление и смысл уже были заданы
как «частный случай». Новые строгие связи частный-общий добавляйте как
`generalization`; старые `special_case` переносите на `generalization` только
когда это действительно та же модель с подстановкой параметров.

Если задача является прямой переформулировкой уже имеющейся карточки, не
создавайте дубль. Добавьте новый источник к существующей карточке или явно
заполните `novelty` и relation к ближайшему классическому шаблону. Новая
родственная карточка нужна только тогда, когда меняется математическая сила:
другая стратегия, другая нижняя оценка, обобщение до произвольного `n`, новый
красивый частный случай или существенно иной источник трудности.

## 5. Эскалация

Если меняется математическая сила условия, стратегия не покрывает крайний случай
или нижняя оценка не доказана, не повышайте статус. Оставьте
`needs_human_review` и коротко напишите, что именно не проверено.

## 6. Изображения

Добавляйте изображения только там, где они реально нужны для понимания условия или решения. Не создавайте пустые блоки и не переносите в картинку текст, который удобно записать в `text`.

Формат поля внутри `statements.*[]`, `ideas[]`, `strategies[]` или `impossibility_proofs[]`:

```json
"figures": [
  {
    "id": "fig-short-name",
    "asset": "data/assets/images/<problem-id>/<name>.webp",
    "alt": "Что видно на изображении.",
    "caption": "Короткая подпись для читателя.",
    "source_id": "src-example",
    "status": "source_verified"
  }
]
```

Правила:

- храните файлы отдельно, не вставляйте base64 в JSON/YAML или HTML;
- используйте безопасный относительный путь от корня репозитория, обычно `data/assets/images/<problem-id>/...`; существующие малые иллюстрации в `data/assets/examples/...` допустимы;
- предпочитайте WebP, PNG или JPEG разумного размера; не храните огромные сканы страниц, вырезайте только нужный фрагмент;
- обязательно заполняйте `alt`, `caption`, `status` и `source_id`; если источника нет в реестре, временно используйте `source_note`, но лучше завести `source_id`;
- картинка в условии показывается вместе с условием, картинка в стратегии или доказательстве видна только внутри раскрытого блока решения.

## 7. Viewer: локальный прогресс, заметки и отчеты

Локальный прогресс и заметки пользователя являются данными браузера, а не частью карточки. Не добавляйте их в YAML задач и не считайте их редакционным статусом: viewer хранит их в `localStorage` под ключом `incomplete-info-db:local-user-data:v1`, а пользователь может экспортировать/импортировать JSON или сбросить данные.

Форма `Сообщить об ошибке` в статическом viewer только формирует отчет для копирования или `mailto`; она не создает GitHub issue и не отправляет данные на сервер. Адрес для `mailto` задается в `FEEDBACK_CONFIG.email` в `tools/build_viewer.py`; если появится внешний endpoint, интерфейс должен явно отличать подготовку отчета от успешной отправки.

## 8. Viewer: интерактивные задачи

Поле `interactive` можно добавлять только к карточкам, где интерактив воспроизводит исходную задачу как самостоятельную проверку действий читателя. Интерактив не заменяет условие, не меняет математическую силу карточки и не должен содержать стратегию, идею решения, оптимальное первое взвешивание или другие подсказки.

Перед добавлением нового типа интерактива проверьте:

- скрытое пространство состояний конечно и явно описано параметрами YAML;
- цель проверяется без чтения решения: например `identify_coin`, `identify_coin_and_sign`, `identify_one_counterfeit`, `prove_impossible`, `choose_safe_door`;
- режим `random` используется для одного случайного скрытого состояния, `cheater` - только когда можно честно выбрать самый неудобный совместимый исход, `exhaustive` - только когда пользователь строит стратегию для всех состояний;
- `objective: "prove_impossible"` используется для интерактива невозможности и должен идти только с `modes: ["exhaustive"]`: цель такого UX - показать хотя бы одну ветку, где после лимита остается несколько совместимых кандидатов;
- В `exhaustive`-режиме viewer может закрывать ветви как `covered` только при явно проверенной симметрии, на любом уровне дерева. Разрешены только явные преобразования множества кандидатов: для `single_counterfeit_unknown_direction` это глобальная замена `heavier/lighter` на тех же монетах; для известных одиночных фальшивых монет, `paired_light_counterfeits`, `multiple_light_find_one` и `grouped_light_counterfeits` это перестановка монет, индуцированная зеркальной заменой текущих левой и правой чаш и сохраняющая модель состояний (пары или группы с теми же ограничениями). Ветка `balance` с неравенствами не склеивается, а совпадение только по числу кандидатов не является основанием для `covered`.
- обычный режим не показывает полный список кандидатов, таблицу кодов, готовый первый ход или другой объект, который фактически раскрывает решение;
- если карточка параметрическая, фиксированный малый `interactive`-случай явно остается той же моделью, а не новой задачей.
- если поисковый агент добавил новые карточки про взвешивания, не прикрепляйте
  интерактив сразу: сначала отдельная разведка должна описать скрытые состояния,
  действия пользователя, проверку ответа, режимы `random/cheater/exhaustive` и
  приоритет разработки; затем отдельный разработчик реализует интерактив, а
  тестировщик проходит его в viewer с визуальной проверкой;
- после добавления нового типа интерактива обновите одновременно YAML-схему,
  `tools/validate.py`, self-tests и правила ниже. Схема и валидатор не должны
  расходиться по списку `type`, `objective` и обязательных полей.

Подробный список следующих кандидатов и ТЗ для новых типов лежит в `docs/reviews/interactive-next-candidates.md`.

Для первого поддержанного типа используется формат:

```json
"interactive": {
  "type": "single_counterfeit_weighing",
  "coin_count": 25,
  "counterfeit_weight": "lighter",
  "max_weighings": 3,
  "objective": "identify_coin",
  "modes": ["random"]
}
```

Обязательные поля для `single_counterfeit_weighing`:

- `type: "single_counterfeit_weighing"` - ключ JS-рендерера во viewer;
- `coin_count` - число одинаковых на вид пронумерованных монет;
- `counterfeit_weight` - известное направление фальшивой монеты: `lighter` или `heavier`;
- `max_weighings` - лимит взвешиваний;
- `objective: "identify_coin"` - цель: найти фальшивую монету; для карточек невозможности допустимо `objective: "prove_impossible"`.

Для числовых взвешиваний стопок/мешков/монет используйте `type: "numeric_linear_signature"`. Для ровно одной фальшивой стопки задавайте `objective: "identify_fake_bag"`, `state_model: "single_fake_bag"`, `fake_bag_count: 1`, `counterfeit_weight`, `counterfeit_delta`, `genuine_weight`, `observation_model: "actual_weight"` и не кладите в YAML готовый вектор количеств монет. Для подмножества фальшивых мешков используйте `objective: "identify_fake_bag_subset"` с `allow_empty_subset`/`exclude_all_fake`. Для фиксированного числа фальшивых монет используйте `objective: "identify_fake_coin_set"`, `state_model: "fixed_fake_count"`, `fake_bag_count`, `object_kind: "coin"` и `selection_model: "subset"`; конфиг не должен содержать готовую последовательность подмножеств.

Для не-взвешивательных числовых тестов вида "выбрать подмножество объектов и получить количество скрытых отмеченных объектов" используйте `type: "subset_signature_protocol"`. Обязательные поля: `object_count`, `max_tests`, `objective: "identify_magic_subset"`. Опционально можно задать только нейтральные `object_labels` и `modes`; YAML не должен содержать готовые проверочные подмножества или матрицу кодов. Проверка стратегии во viewer принимает только инъективное отображение скрытое подмножество -> кортеж числовых ответов и при конфликте показывает две разные скрытые конфигурации с одинаковой подписью.

Для малых BAS-карточек, где скрыто одно число и пользователь выбирает вопросы вида "принадлежит ли число этому подмножеству?", используйте `type: "balanced_subset_question_code"`. Обязательные поля: `object_count`, `max_tests`, `target_sum`, `objective: "identify_hidden_number"`. YAML не должен содержать готовые подмножества; viewer проверяет, что каждое выбранное подмножество имеет нужную сумму и что все скрытые числа дают разные двоичные ответы.

Для частного протокола "первый обязан перевернуть ровно одну монету, второй угадывает позицию ключа по итоговой раскладке" используйте `type: "xor_single_flip_protocol"`. Обязательные поля: `position_count`, `objective: "identify_key_position"` и режимы вроде `["random", "cheater", "exhaustive"]`. YAML задает только число позиций и режимы, а не готовую таблицу ходов; viewer сам строит начальные биты, позицию ключа и exhaustive-проверку всех `position_count * 2^position_count` состояний.

Для поиска движущейся цели на конечном графе используйте `type: "moving_target_graph_search"`. Обязательные поля: `vertices`, `edges`, `check_size`, `max_tests`, `objective: "capture_hidden_moving_target"`. Конфиг задает только граф, лимит и размер проверки; он не должен содержать готовую последовательность проверяемых вершин. После неудачной проверки цель переходит в соседнюю вершину; `cheater` и `exhaustive` должны работать с множеством всех совместимых текущих вершин, а не с одним заранее выбранным путем.

Для конечного карточного протокола, где пользователь задает таблицу соответствий
между неупорядоченными парами, используйте `type:
"finite_pair_matching_protocol"`. Обязательные поля: `card_count`,
`hidden_count: 2`, `shown_count: 2`, `objective: "identify_hidden_pair"` и
режимы вроде `["sandbox", "exhaustive"]`. YAML не должен содержать готовую
таблицу соответствий: viewer строит все скрытые пары сам, а пользователь
выбирает показываемую пару для каждой строки. Проверка принимает стратегию
только если каждая показываемая пара не пересекается со спрятанной и все
показываемые пары различны, так что обратное декодирование однозначно.

Для фокуса Чейни с пятью картами и обычной колодой используйте
`type: "fitch_cheney_card_trick"`. Обязательные поля: `deck_size: 52`,
`hand_size: 5`, `shown_cards: 4`, `hidden_cards: 1`,
`objective: "identify_hidden_card"` и режимы вроде
`["random", "exhaustive", "sandbox"]`. YAML задает только модель фокуса,
а не готовую пару одной масти или порядок карт. Viewer сам выбирает ход
ассистента, декодирует скрытую карту по четырем показанным картам и в
`exhaustive` проверяет все 5-карточные руки стандартной колоды.

Для модели, где неизвестно, легче или тяжелее фальшивая монета, используйте `type: "single_counterfeit_unknown_direction"`. В ней обязательны `coin_count`, `max_weighings`, `objective: "identify_coin_and_sign"`/`"identify_coin_and_direction"` или, если знак не требуется, `"identify_coin_only_unknown_direction"`; `counterfeit_weight` не задается. Если в условии дана настоящая монета для сравнения, добавьте `known_genuine_count` или `has_known_genuine`. Режим `cheater` в этой модели хранит совместимые скрытые состояния `(монета, heavier/lighter)` и после каждого взвешивания выбирает честный исход с максимальным числом оставшихся состояний; при равенстве используется стабильный tie-breaker по истории исходов.

Для задач с целью "выбрать кучку, в которой точно нет фальшивого объекта" используйте `type: "safe_pile_balance_certificate"`, `objective: "identify_safe_pile"`, `pile_sizes` или `piles`, `max_weighings` и `require_equal_pan_counts: true`. Конфиг описывает только размеры/состав кучек и модель скрытого состояния; не записывайте в YAML оптимальное взвешивание или правило выбора.

Для задач с несколькими заведомо легкими фальшивыми монетами, где достаточно назвать хотя бы одну легкую монету, используйте `type: "multiple_light_find_one"` с `coin_count`, `counterfeit_count`, `max_weighings` и `objective: "identify_one_light_coin"`. Ветка или финальный ответ принимается только тогда, когда названная монета есть в каждом совместимом скрытом состоянии.

Для задач с ржавыми чашечными весами, где малый перевес не дает надежного направления, используйте отдельный тип `threshold_balance_counterfeit_sets`: обязательны `coin_count`, `counterfeit_count`, `counterfeit_weight: "lighter"`, `genuine_weight`, `counterfeit_delta`, `reliable_difference`, `max_weighings`, `objective: "identify_all_counterfeits"` и режимы. Не заменяйте такую модель обычными `multiple_light_find_one` или `grouped_light_counterfeits`: исход `no_reliable_tilt` должен объединять все состояния, в которых абсолютная разница масс меньше порога.

Для задач, где после неравного сравнения прибор удаляет монету из более тяжелой стороны, не используйте обычный `single_counterfeit_weighing`. Для модели USAMTS с роботом Золтаром используется `type: "zoltar_heavier_hand_removal"`: обязательны `coin_count`, `real_count`, `counterfeit_count`, `max_weighings` и `objective: "identify_one_genuine_coin_not_removed"`. Скрытое состояние хранит множество настоящих монет и уже забранные монеты. В `random` удаляемая монета выбирается случайно из более тяжелой руки, а в `cheater` и `exhaustive` каждая допустимая удаляемая монета является отдельной веткой; ответ принимается только если выбранная монета не забрана и настоящая во всех совместимых состояниях.

Для модели, где скрыто сломан не объект, а прибор, используйте отдельный тип `faulty_scale_identification`. Обязательные поля: `scale_count`, `faulty_scale_count: 1`, `max_weighings`, `objective: "identify_faulty_scale"`, `weighable_objects: "scales"`. Такой интерактив должен явно давать пользователю выбор прибора для взвешивания и не описывать неисправность как фальшивую монету.

Для модели, где сломан один из нескольких приборов, а цель - найти монету,
используйте отдельный тип `broken_scale_counterfeit_coin`: скрытое состояние
включает и фальшивую монету, и сломанные весы, но ответ проверяется по цели
карточки. Если сломанные весы могут при каждом использовании давать произвольный
исход, не описывайте их как прибор с заранее фиксированным ложным знаком.

Для модели `heaviest_coin_one_broken_scale` цель - найти самую тяжелую монету
среди попарно разных масс, когда одна пара весов испорчена. Проверка ответа не
должна требовать восстановить полный порядок масс или назвать сломанные весы.

`modes` необязателен; допустимые значения сейчас: `random`, `cheater`, `exhaustive`, `challenge`, `sandbox`, `guided`. Для `single_counterfeit_weighing` и `single_counterfeit_unknown_direction` во viewer открыты `random`, `cheater`, `exhaustive`; показывайте в UI только режимы, явно перечисленные в `modes` конкретной карточки. Не добавляйте интерактив массово: сначала нужна явно подходящая карточка и проверка, что условие, профили и интерактив описывают одну и ту же модель.

Для задачи с заключенными и ящиками используйте `type: "permutation_cycle_protocol"`. Обязательные поля: `prisoner_count`, `box_count`, `max_openings`, `objective: "all_agents_find_own_state"`. Конфиг задает только размеры и режимы; перестановка номеров по ящикам является скрытым состоянием viewer. `random` строит случайную перестановку, `cheater` может выбирать перестановку с циклом длиннее лимита, а `exhaustive` должен классифицировать перестановки по типам циклов, а не перебирать все `n!` варианты в интерфейсе.

Режимы цветовых статусов монет (`ручной`, `с проверкой`, `авто`) являются состоянием viewer, а не полями YAML-карточки. Проверка статусов должна сравнивать отметки пользователя со всеми совместимыми скрытыми состояниями после истории взвешиваний, а не с одним случайно выбранным состоянием режима `random`.

Во viewer переключение на вкладку `Интерактив` не раскрывает блоки `Идеи` и `Решение и оценки`. Эти блоки остаются обычными закрытыми `details`, и интерактивный рендерер не должен программно их открывать.
