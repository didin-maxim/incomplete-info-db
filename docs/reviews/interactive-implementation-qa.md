# QA acceptance for the next strong interactives

Роль этого файла - приемочный чеклист для интегратора после реализации новой очереди. Он не заменяет `docs/INTERACTIVE_ENGINE_GUIDE.md` и `docs/AI_CARD_RULES.md`: сначала проверяем фактическое поведение в браузере и selftests, затем переносим устойчивые правила в общие документы.

## Область приемки

Проверяются 5 ближайших кандидатов:

1. `four-guineas-exactly-two-counterfeits-verification` - property verification.
2. `ukmt-open-ended-2013-task-four-42-counterfeit-coins` как малый 6-монетный случай.
3. `problems-ru-35224-noisy-balance-four-coins` - noisy balance.
4. `problems-ru-65817-six-coins-digital-scale-unknown-weights` - numeric calibration.
5. `emelyanov-expert-judge-two-counterfeits-two-weighings` как малый expert judge two-counterfeits.

Не принимаем слабую реализацию ради закрытия очереди. Если сильный exercise не получается, кандидат должен быть отложен или явно переведен в `review_only`/`demonstration`, а не маскироваться под интерактив.

## Общий browser-чеклист для каждого нового типа

- Открыть собранный viewer, найти целевую карточку, перейти на вкладку `Интерактив`.
- Проверить, что вкладка `Интерактив` сама не раскрывает `Идеи` и `Решение и оценки`.
- Проверить первичный экран: понятны скрытое состояние, цель пользователя, лимит ходов и смысл цветов/символов. Если без легенды непонятно, это блокер или нужен `visual_legend_needed: true`.
- Проверить, что конкретный скрытый мир не раскрыт до финальной проверки. Запрещены подсветка настоящего ответа, готовая таблица решения, фактическая пара/знак/расклад до `check`.
- Проверить, что действие пользователя содержательное: построение хода, дерева, сертификата, таблицы или финального ответа. Нажатия `далее`, перебор готового разбора и просмотр совместимых состояний не считаются упражнением.
- Проверить `random`, если режим есть: выбирается один скрытый мир, результаты согласованы с ним, финальная проверка не использует чужой мир и после ошибки раскрывает только минимально нужный контрпример.
- Проверить `cheater`, если режим есть: скрытое состояние не фиксируется заранее; после каждого действия остается множество совместимых состояний; adversary выбирает ответ, который ломает недостаточную стратегию или сохраняет максимум неоднозначности.
- Проверить `exhaustive`, если режим есть: проверяются все релевантные состояния/ветки, результат не зависит от одного случайного расклада, тяжелые переборы показаны агрегированно.
- Проверить отличие режимов визуально и логически. Если `random`, `cheater` и `exhaustive` дают одинаковую кнопку с одинаковым результатом, режимы не приняты.
- Проверить плохой сценарий: заведомо неверный ответ или неполный сертификат получает понятную ошибку без раскрытия полного решения.
- Проверить хороший сценарий: известная корректная стратегия проходит, статус успеха связан с целью карточки, а не с техническим завершением шагов.
- Проверить layout на узком экране и обычном desktop: элементы не налезают, таблицы не ломают панель, кнопки с длинным текстом не растягивают сетку.
- Проверить, что английские служебные ключи не попали в пользовательский UI, кроме технических `type`/`mode` в debug-контексте.

## Кандидат 1: property verification

Целевой кандидат: `four-guineas-exactly-two-counterfeits-verification`.

Browser acceptance:

- Пользователь проверяет свойство, а не угадывает номер монеты: финальный ответ имеет вид "свойство выполнено / не выполнено".
- Скрытая модель содержит все 16 двувесовые раскладки 4 монет; в UI не показывается текущая раскладка до проверки.
- `exhaustive` проверяет дерево по всем 16 раскладкам и принимает только стратегию, которая корректно классифицирует свойство для каждой.
- `random` прогоняет одну ветку и не делает вид, что случайный успех доказывает стратегию.
- `sandbox` помогает отлаживать ходы, но не заменяет exhaustive-проверку.
- Визуально ясно, что чашечное взвешивание задает вопрос о свойстве, а не обычный поиск фальшивой монеты.

Selftests:

- Генерация ровно 16 состояний для 4 монет с двумя возможными весами.
- Подсчет классов свойства: положительный и отрицательный классы непустые, сумма равна 16.
- Функция outcome для любого допустимого взвешивания возвращает согласованный результат для каждого состояния.
- Фильтрация после результата сохраняет только совместимые состояния и не смешивает состояние с целевым свойством.
- Exhaustive-проверка принимает известный корректный сертификат/дерево и отвергает дерево, которое совпадает с ним на random-ветке, но ошибается на другом классе.
- Проверка финального ответа отвергает состояние, где свойство истинно, при ответе "нет", и наоборот.

## Кандидат 2: small UKMT

Целевой кандидат: `ukmt-open-ended-2013-task-four-42-counterfeit-coins` как малый 6-монетный режим.

Browser acceptance:

- UI явно подписан как малый учебный случай 6 монет, связанный с большой задачей, но не подменяющий 42 монеты кликалкой.
- Скрытая модель содержит 12 состояний `(coin, lighter/heavier)`.
- Финальный ответ требует только номер монеты; знак не должен быть обязательным и не должен заранее раскрываться.
- `random` фиксирует одну пару `(coin, sign)`, но итог проверяет только номер.
- `cheater` хранит совместимые пары и может отвечать так, чтобы оставить две пары с разными монетами, если стратегия слабая.
- `exhaustive` проверяет все 12 состояний и принимает дерево, где листья однозначны по номеру, даже если знак в листе не определен.
- UI не требует от пользователя различать два знака одной и той же монеты как разные ответы.

Selftests:

- Генерация ровно 12 состояний для 6 монет и двух знаков.
- Projection-test: две пары с одной монетой, но разными знаками считаются одним допустимым финальным номером.
- Exhaustive branch status: лист с состояниями `coin i light` и `coin i heavy` считается решенным для objective `identify_coin_only_unknown_direction`.
- Неверный лист с двумя разными номерами не считается решенным, даже если все состояния имеют один знак.
- `cheater` после взвешивания выбирает ветку по числу разных возможных номеров, а не только по числу пар.
- Known valid small strategy проходит в пределах лимита, а стратегия, которая называет знак или использует 42 UI-объекта, не является accepted exercise.

## Кандидат 3: noisy balance

Целевой кандидат: `problems-ru-35224-noisy-balance-four-coins`.

Browser acceptance:

- UI явно объясняет модель ненадежного равновесия: надежны только перекосы; физическое равенство не является честным третьим исходом.
- Пользователь выбирает сравнения и финально называет монету и знак при 8 скрытых состояниях.
- Нельзя использовать обычный three-way balance как готовый движок без изменения семантики результата `balance`.
- `cheater` должен уметь отвечать adversarially при равенстве так, чтобы сохранить совместимые состояния.
- `exhaustive` проверяет все состояния и все допустимые noisy-ответы, а не только физические исходы.
- В UI отдельно видны "физический результат" и "ответ прибора", если оба показываются; они не должны сливаться в один цвет.

Selftests:

- Генерация ровно 8 состояний `(coin, sign)` для 4 монет.
- Outcome-test: при ненулевой разнице результат перекоса детерминирован; при нулевой разнице допустимы оба noisy-ответа по принятой модели.
- Фильтрация noisy-ответа не отбрасывает состояния, где физическое равенство могло дать этот ответ.
- Обычная стратегия для надежных чашечных весов должна провалиться, если она опирается на честный `balance`.
- Exhaustive-проверка принимает стратегию, которая различает все 8 состояний в заявленном лимите.
- `cheater` выбирает ветку с максимальной неоднозначностью и не фиксирует скрытый coin/sign до необходимости.

## Кандидат 4: numeric calibration

Целевой кандидат: `problems-ru-65817-six-coins-digital-scale-unknown-weights`.

Browser acceptance:

- UI показывает цифровое взвешивание как сумму выбранного подмножества, а не как чашечные весы.
- Скрыты не только фальшивая монета, но и параметры масс настоящей/фальшивой монеты или их допустимые соотношения.
- Пользователь выбирает подмножества и строит калибровку; интерактив не должен просто показывать формулу решения.
- `random` выбирает конкретные параметры и монету, но не раскрывает их до проверки.
- `cheater` сохраняет множество совместимых `(coin, parameters)` и выбирает ответ, который ломает недокалиброванную стратегию.
- `exhaustive` проверяет символические классы или конечную дискретизацию, явно достаточную для карточки; нельзя принимать по одному числовому примеру.
- Визуально понятно, какие результаты являются наблюдениями, какие - ограничениями, какие - финальным выводом пользователя.

Selftests:

- Нормализация конфигурации: 6 монет, допустимая модель неизвестных масс, цель `identify_coin` или ближайшая точная цель.
- Символический outcome для подмножества зависит от выбранной монеты и параметров, а одинаковые наблюдения объединяют совместимые состояния.
- Calibration-test: две разные параметрические реализации с одинаковой фальшивой монетой не требуют разного финального ответа.
- Counterexample-test: существуют две совместимые реализации с разными монетами после слабого набора запросов, и check отвергает финальный ответ.
- Exhaustive или bounded symbolic test принимает известный протокол и доказывает единственность номера для всех допустимых параметров.
- Numeric edge cases: равные/крайние допустимые массы, пустое подмножество, полное подмножество и повторный запрос не ломают состояние.

## Кандидат 5: expert judge two-counterfeits

Целевой кандидат: `emelyanov-expert-judge-two-counterfeits-two-weighings` как малый случай.

Browser acceptance:

- UI различает роли: эксперт знает пару и знак, судья видит только публичные результаты и проверяет сертификат.
- Малый случай самодостаточен: 6 монет, ровно две равные фальшивые, обе легче или обе тяжелее, 2 публичных взвешивания.
- Пользователь предъявляет две проверки/сертификат, а не просматривает готовый официальный разбор.
- Скрытая пара и знак не раскрываются до проверки; после ошибки показывается минимальный контрпример.
- `sandbox` пригоден для выбора сертификата экспертом, но приемка требует `exhaustive` для судьи.
- `exhaustive` перебирает все пары и оба общих знака, затем проверяет, что публичные результаты вынуждают заявленную пару и знак.
- Визуальная легенда должна отделять "выбранные экспертом монеты", "чаши проверки", "результаты судьи" и "совместимые скрытые пары".

Selftests:

- Генерация всех hidden states: `C(6, 2) * 2 = 30` состояний.
- Outcome-test для двух равных фальшивых одного знака на чашечном взвешивании.
- Certificate-test: известный корректный малый сертификат оставляет ровно одну пару и знак.
- Ambiguity-test: сертификат с одной проверкой или симметричными взвешиваниями оставляет минимум два совместимых состояния и отвергается.
- Role-test: judge-проверка не использует private assignment эксперта, кроме как для генерации ожидаемых публичных результатов.
- Error-report test: при провале возвращается контрпример `(pair, sign)` или две неразличимые пары, но не полный перебор всех 30 состояний в UI.

## Правила базы после реализации

После того как код и YAML реально появятся и пройдут приемку, обновить общие правила:

- В `docs/INTERACTIVE_ENGINE_GUIDE.md` добавить новые или уточненные семейства движков: property verification, noisy balance, numeric calibration, expert judge two-counterfeits, small UKMT as projected-answer unknown-sign counterfeit.
- В таблице "Что копировать для новых задач" указать, когда брать эти движки, а когда оставаться на существующих `single_counterfeit_unknown_direction`, `numeric_linear_signature`, `expert_judge_certificate` или `finite_binary_state_protocol`.
- В `docs/AI_CARD_RULES.md` зафиксировать, что property verification - это проверка свойства по всем скрытым состояниям, а не поиск объекта.
- Добавить правило про projected answers: если цель слабее скрытого состояния, например "назвать монету без знака", exhaustive-лист решен только когда все совместимые состояния дают один публичный ответ.
- Добавить правило noisy balance: результат `balance` нельзя наследовать из обычных чашечных весов без явной модели надежности.
- Добавить правило numeric calibration: один числовой пример не доказывает интерактив; проверка должна работать по параметрам, классам параметров или обоснованной конечной дискретизации.
- Добавить правило expert judge: exercise принимается только если пользователь предъявляет проверяемый сертификат, а judge-проверка перебирает скрытые состояния без доступа к private role-data.
- Добавить правило small-case closure: большой источник можно закрыть малым случаем только если сохранены скрытая модель, цель и ключевой конфликт наблюдений; иначе это отдельная демонстрация.
- Обновить список selftests в guide: для каждого нового движка должен быть хотя бы один positive strategy, один adversarial/negative scenario и одна проверка скрытия/проекции состояния.

Не обновлять правила раньше фактической реализации: иначе документация начнет обещать движки, которых еще нет в allowlist/viewer.

## Когда кандидата отложить

Откладываем вместо слабой реализации, если выполняется хотя бы одно условие:

- Невозможно сформулировать скрытое состояние и наблюдение без противоречия с условием карточки.
- Нет содержательного действия пользователя, кроме кликов по готовому разбору или просмотра совместимых состояний.
- `random`, `cheater`, `exhaustive` невозможно развести логически; все режимы проверяют один пример.
- Проверка принимает стратегию, которая работает только на одном зафиксированном hidden state.
- UI вынужден раскрыть решение или скрытый мир до того, как пользователь сделал проверяемое предъявление.
- Полный размер задачи превращает экран в кликалку на десятки/сотни объектов, а малого самодостаточного случая или агрегированного протокола нет.
- Нет надежного negative selftest: нельзя автоматически показать, что слабая стратегия отвергается.
- Модель требует новой математики, которую реализация не проверяет, например symbolic calibration подменяется floating-point примером.
- Визуальная модель настолько непонятна без длинного текста, что пользователь не может отличить публичные данные от скрытых.
- Реализация требует правки viewer/YAML в обход согласованного движка и не укладывается в текущую очередь.

Решение об откладывании фиксировать в review-файле с причиной и минимальным следующим шагом: "нужен selftest про проекцию", "нужна symbolic-модель", "нужен малый случай", "оставить demonstration".

## Финальная приемка перед коммитом

- `git status --short` просмотрен, чужие изменения не откатывались.
- Для каждого из 5 кандидатов есть YAML-конфиг с корректным `type`, `objective`, `modes`, `presentation` и при необходимости `interactive_strength`, `estimated_user_actions`, `mode_action_estimates`.
- `tools/validate.py` знает новые type/objective/modes или кандидат использует существующий тип без семантической подмены.
- `tools/build_viewer.py` рендерит каждый новый тип и не показывает режимы, которых нет в YAML.
- `tools/weighing_cheater_selftest.js` или отдельный selftest покрывает все пункты из разделов выше.
- В браузере вручную проверены `random`, `cheater`, `exhaustive`/`sandbox` для каждого кандидата, включая успешный и ошибочный сценарий.
- Проверено, что вкладка `Интерактив` не раскрывает `Идеи` и `Решение и оценки`.
- Для тяжелого exhaustive есть агрегаты, предупреждение или малый случай; нет огромной кликалки.
- После реализации обновлены `docs/AI_CARD_RULES.md` и `docs/INTERACTIVE_ENGINE_GUIDE.md` только теми правилами, которые реально поддержаны кодом.
- Запущены минимальные команды:

```powershell
python tools\check_encoding.py
python tools\validate.py
node tools\weighing_cheater_selftest.js
python tools\build_viewer.py
```

- В финальном отчете перечислены проверенные карточки, режимы, selftests, browser-сценарии и все отложенные кандидаты с причиной.
