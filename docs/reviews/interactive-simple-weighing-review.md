# Ревизия простых интерактивов по взвешиваниям

Дата: 2026-05-25.

Область: вводные и малые интерактивы вокруг `weighings` с `difficulty.main` = `intro`/`olympiad_medium`, низким `local_score`, небольшим ожидаемым числом действий или спорным `presentation`. Использованы YAML, `interactive-status`, `interactive-current-map`, `interactive-demonstration-quality-review`, а также свежие аудиты по single-counterfeit, broken/expert и structured/numeric weighing.

## Вывод

Сильные упражнения здесь те, где пользователь реально строит взвешивание, дерево, пару тестов или финальный ответ, а viewer проверяет скрытое состояние. Демонстрациями лучше считать фиксированные наблюдения и нижние оценки: там пользователь не решает экземпляр, а видит, почему готовые данные или число исходов принуждают вывод.

Критерии для вводных weighing-карточек:

- `random` полезен, когда скрытое состояние заставляет пользователя применить стратегию на одном экземпляре.
- `cheater` полезен как учебный режим, если подсветка кандидатов не раскрывает всю задачу до первого осмысленного хода.
- `exhaustive` полезен для доказательства гарантии дерева; в тяжелых случаях его надо описывать как проверку схемы, а не быструю игру.
- `sandbox` полезен только там, где пользователь строит план или свободный код; для обычного адаптивного поиска монеты он вводит в заблуждение, если движок фактически поддерживает только `random/cheater/exhaustive`.
- Визуальные элементы должны работать на модель: монеты дают скрытые состояния, чаши/детекторы дают наблюдения, цвета кандидатов показывают совместимость, а метки типов нужны только когда меняют правило чтения перекоса.

## Правила для очереди

1. Для первых публичных weighing-упражнений продвигать `heavier-9`, `lighter-8`, малый LKTG на 3 монеты и компактные типозависимые задачи.
2. `heavier-4` и `spb-primary` держать как демонстрации: первая объясняет нижнюю оценку, вторая разбирает уже данные измерения.
3. `25/27` монет не смешивать: `27` полезен как полная емкость `3^3`, `25` слабее и должен идти после 9 монет.
4. Для неисправных детекторов и 17-монетной parity-задачи `exhaustive` подписывать как проверку гарантии по большому пространству состояний.
5. Режим, который не меняет проверяемое действие пользователя, лучше не добавлять: особенно `sandbox` в адаптивных single-counterfeit задачах без отдельного построителя дерева.
