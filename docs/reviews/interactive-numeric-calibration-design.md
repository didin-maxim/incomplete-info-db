# Дизайн `numeric_weight_calibration`

Дата: 2026-05-25.

Область: `problems-ru-65817-six-coins-digital-scale-unknown-weights`.

## Решение

В этом проходе не добавлять `interactive` в карточку и не писать viewer-код.

Задача подходит для сильного интерактива, но это не узкое расширение `numeric_linear_signature`. Нужен новый движок для непрерывных параметров, условно `numeric_weight_calibration`: он должен проверять кандидатов на фальшивую монету через малые линейные системы по неизвестным массам настоящей и фальшивой монет. Показ готовых формул был бы слабой демонстрацией, а конечная выборка масс была бы математически неверной.

## Скрытая модель

Есть шесть видимых монет. Скрытое состояние состоит из трех частей:

- `i in {1,2,3,4,5,6}` - номер фальшивой монеты;
- `g` - масса настоящей монеты;
- `f` - масса фальшивой монеты;
- ограничения: `g > 0`, `f > 0`, `f != g`.

Для выбранного подмножества `S` цифровые весы возвращают точный общий вес

```text
W(S) = |S| * g + 1_{i in S} * (f - g).
```

Если положить `d = f - g`, каждое наблюдение дает линейное уравнение

```text
|S| * g + 1_{i in S} * d = W(S),
g > 0,
g + d > 0,
d != 0.
```

После истории `(S_t, W_t)` монета `i` совместима с наблюдениями тогда и только тогда, когда эта система имеет хотя бы одно решение `(g,d)`. Ветка решена ровно тогда, когда все совместимые решения дают один и тот же номер фальшивой монеты. Сами массы восстанавливать не нужно.

## Почему не `numeric_linear_signature`

Текущий `numeric_linear_signature` работает с конечным множеством скрытых состояний: подмножества фальшивых мешков, один фальшивый мешок, явные fake sets, signed delta states, выбранный вес мешка. Числовой ключ получается прямым вычислением фиксированного скрытого состояния на пользовательском векторе коэффициентов. Даже режим `projective_signed_deviation` убирает только один неизвестный общий масштаб.

В этой задаче есть два непрерывных общих параметра, а масса настоящей монеты дает зависящий от хода член `|S| * g`. Проверка должна отвечать не на вопрос "совпали ли две конечные подписи", а на вопрос:

```text
существует ли положительная пара (g,f), f != g,
которая делает данный числовой протокол совместимым с этой монетой?
```

Попытка закодировать это через `hidden_states` или `projective_signed_deviation` либо вынесет ручную алгебру в интерфейс, либо сведет задачу к конечной выборке масс. Оба варианта нарушают критерий: ветка считается решенной только если номер фальшивой монеты одинаков для всех совместимых `g,f`.

## Проверка решения карточки

Решение карточки согласуется с этой моделью:

1. Взвесить `{1,2}` и назвать половину показания `a`.
2. Взвесить `{3,4}` и назвать половину показания `b`.
3. Если `a = b`, то монеты 1-4 настоящие, а фальшивая - 5 или 6. Взвесить монету 5: показание `a` означает, что фальшива монета 6, иначе фальшива монета 5.
4. Если `a != b`, то фальшивая среди 1-4. Взвесить `{1,3,5}`. Для случаев, когда фальшивы 1, 2, 3, 4, показания соответственно равны `2a+b`, `3b`, `a+2b`, `3a`; при `a != b` эти четыре значения различны.

Будущий интерактив не должен просить пользователя работать с этими формулами. Пользователь выбирает подмножества, а движок сам доказывает совместимость или несовместимость номеров монет по числовой истории.

## Обязательный будущий тип

Предлагаемый YAML:

```yaml
interactive:
  type: numeric_weight_calibration
  presentation: exercise
  object_count: 6
  object_kind: coin
  max_weighings: 3
  objective: identify_counterfeit_coin
  state_model: single_counterfeit_unknown_true_and_fake_weight
  observation_model: total_subset_weight
  query_model: subset
  mass_variables:
    genuine: g
    counterfeit: f
  mass_constraints:
    positive: true
    distinct: true
  modes: [random, cheater]
```

Обязательная семантика:

- `object_count`: число монет;
- `max_weighings`: жесткий лимит ходов;
- `objective: identify_counterfeit_coin`: ответ - только номер монеты;
- `state_model: single_counterfeit_unknown_true_and_fake_weight`: одна фальшивая, масса настоящей неизвестна, масса фальшивой неизвестна;
- `observation_model: total_subset_weight`: одночашечные цифровые весы возвращают точную сумму выбранного подмножества;
- `query_model: subset`: ход выбирает подмножество монет, без левой и правой чаши;
- `mass_constraints`: как минимум положительные массы и `f != g`.

Опциональные поля позже могут задавать подписи объектов, диапазоны целых масс для `random`, точность отображения или готовые примеры. YAML не должен содержать формулы решения или дерево решений для этой карточки.

## Требования к движку

Базовая проверка:

- нормализовать историю в строки `[размер подмножества, содержит ли подмножество кандидата]`;
- для каждой монеты-кандидата решать линейную систему по `(g,d)` с ограничениями `g > 0`, `g + d > 0`, `d != 0`;
- поддержать ранги 0, 1 и 2; при ранге 1 остается аффинная прямая, и для нее тоже нужна проверка неравенств, а не только равенств;
- по возможности использовать точную рациональную арифметику. В `random` можно выбирать целые массы, чтобы все показания были целыми; в `cheater` могут понадобиться рациональные показания-свидетели;
- `branch_status = solved` тогда и только тогда, когда множество совместимых кандидатов проецируется в один номер монеты;
- финальный ответ принимать только если каждая совместимая ветка имеет выбранный номер монеты.

Режим противника:

- хранить текущую числовую историю, а не конечный список дискретных состояний;
- для нового подмножества вычислять, какие показания сохраняют совместимость каждого кандидата;
- выбирать показание, максимизирующее число оставшихся номеров монет; при равенстве можно предпочитать более широкую область допустимых масс и затем более простое отображаемое число;
- не заменять это выборкой пар `(g,f)`.

Полный перебор:

- наивное дерево по всем вещественным показаниям невозможно показать;
- первый релиз может не иметь `exhaustive`, либо должен показывать символические клетки/точки/интервалы с множествами совместимых кандидатов;
- отдельный будущий режим может принимать маленькое дерево решений с предикатами вроде равенства предыдущих показаний, но это не обязательная часть первого движка.

Selftest перед релизом:

- проверить протокол решения для фальшивой монеты `1..6` и нескольких целых пар `(g,f)`;
- ветка равенства: после `{1,2}`, `{3,4}` с равными показаниями совместимы ровно монеты `{5,6}`; после взвешивания монеты 5 ветка решена;
- ветка неравенства: после `{1,2}`, `{3,4}`, `{1,3,5}` кандидаты среди `1..4` разделяются на четыре разных показания при любом `g != f`;
- добавить регрессию, что ветка не считается решенной только потому, что выбранное случайное скрытое состояние одно.
